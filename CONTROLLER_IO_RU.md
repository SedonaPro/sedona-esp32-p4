# Контроллер ESP32-P4: компоненты и проверка

Сборка 15.11.2026 для Waveshare ESP32-P4-ETH / ESP-IDF 6.0.3.
Существующее приложение сохранено; новые объекты добавлены в `/io` и `/service`.

## Что находится в приложении

| Путь | Компонент | Назначение |
|---|---|---|
| `/io/ai1`…`ai4` | AnalogInput | ADC, raw, калиброванные мВ, пересчёт и фильтр |
| `/io/ao1`…`ao2` | PwmOutput | Два PWM-канала, 10 кГц / 12 бит |
| `/io/di1`…`di6` | GpioInput | Шесть дискретных входов |
| `/io/do1`…`do4` | GpioOutput | Четыре дискретных выхода |
| `/io/counter` | PulseCounter | Отдельный аппаратный счётчик фронтов, 64-битный результат |
| `/service/i2c` | I2cService | I²C0 master, write / repeated-start read |
| `/service/spi` | SpiService | SPI2 master, mode 0–3, full duplex |
| `/service/serial` | SerialService | UART1, RX/TX, опциональный DE для RS-485 |
| `/service/rtu` | RtuService | Modbus RTU master **или** slave на UART1 |
| `/service/mqtt` | MqttService | ESP-MQTT publish/subscribe, MQTT/MQTTS |
| `/service/diag` | Diagnostics | CPU каждого ядра, память, стек VM, период и overruns |
| `/service/ota` | OtaService | Обновление кода по HTTPS, проверка сертификата, откат |

Старая демонстрационная папка `/gpio` сохранена для совместимости с приложением.
Число заявленных каналов относится к новой папке `/io`.

## Подключение IO

Все физические точки и сервисы шин при первом запуске выключены, `pin=-1`.
Список `SEDONA_GPIO_ALLOWED_PINS` пока пуст: доступ к аппаратным пинам закрыт.
Перед электрической проверкой нужно согласовать распиновку и включить только
проверенные свободные пины в конфигурации сборки. Общий реестр исключает
одновременный захват пина разными драйверами; Ethernet и консоль зарезервированы.

**AI 0–10 В:** внешний делитель/буфер, защита и RC-фильтр обязательны.
`AnalogInput` измеряет напряжение на входе ADC, а не непосредственно 10 В.
`out = millivolts / 1000 * dividerRatio + offset`; `alpha` — коэффициент
экспоненциального фильтра (0 < alpha <= 1). `valid` и `fault` обязательны
для оценки результата. `dividerRatio` задаётся по фактической схеме и калибровке.

**AO 0–10 В:** PWM на GPIO сам выдаёт только цифровой сигнал уровня 3,3 В.
Нужны внешний фильтр и усилитель с соответствующим питанием. `in` задаётся
в вольтах; по умолчанию `fullScale=10`, значения ограничиваются диапазоном
0…fullScale. `out` — применённая программная уставка, а не измеренная обратная
связь выходного напряжения. Состояние при reset/потере питания определяется
также внешней схемой; программный stop не заменяет аппаратное безопасное состояние.

DI/DO используют `pull`, `invert`, `enabled`, `fault`. Силовые нагрузки и 24 В
подключаются через согласующие входы/выходные каскады. Уровни DI/DO и типы
выходных каскадов ещё не определены. Счётчик считает положительные фронты,
аппаратный фильтр — 1 мкс; `reset` очищает счётчик. Контактный дребезг
механического датчика требует отдельного решения.

## SPI, I²C, UART

Задать параметры при выключенном сервисе. Изменения конфигурации открытого
контроллера требуют выключить сервис, дождаться завершения операции и включить
его заново. Один сервис владеет одним контроллером; I²C в этой версии работает
с одним настроенным адресом устройства за раз.

Заполнить `tx`, задать `rxLength` и `timeoutMs`, включить сервис и вызвать
`transfer`. `busy` устанавливается до завершения, `rx` содержит ответ,
`completed` считает успешные операции. Буферы ограничены 256 байтами.
I²C: адрес 7 бит, 100/400 кГц, запись и затем чтение с repeated start.
SPI: чтение начинается с первого такта; передача дополняется нулями до
max(tx.size, rxLength), CS ведёт аппаратный драйвер.
UART: 8 бит данных, один стоп-бит, parity 0 none / 1 odd / 2 even;
`dePin>=0` включает half duplex. Это интерфейс транзакций с фиксированной
длиной ответа, не непрерывный потоковый логгер.

Транзакции выполняются в отдельных задачах; VM копирует готовые буферы.
`SerialService` и `RtuService` используют UART1 и не должны быть включены
одновременно. Консоль UART0 сохраняется.

## Modbus RTU

Нужен внешний RS-485 трансивер с логическими уровнями 3,3 В и управлением DE.
`role=0` — master, `role=1` — slave. Режим выбирается при выключенном сервисе.
По умолчанию 19200, 8E1; parity настраивается, стоп-бит в этой версии один.
Slave address `unit`: 1…247.

Поддержаны FC1/2/3/4/5/6/15/16, CRC, ответы-исключения, broadcast-запись
в slave. Локальные таблицы: 0 holding, 1 input, 2 coils, 3 discrete;
по 64 адреса в каждой. В master запрос читает/пишет удалённые адреса
`address…address+quantity-1`, результат помещается с индекса 0 локальной
таблицы. FC5/6 берут `writeValue`, FC15/16 — значения из локальной таблицы.
До 64 значений за запрос; адреса в настройках нулевые, не обозначения 40001.

Автоматический опрос (`pollMs`) действует только для FC1…4. Для записи вызвать
`request`. Компонент `ModbusWord` связывает целое значение Sedona с таблицей
через `serviceId`, `table`, `index`, `write`, `in/out`. В этой версии нет
автоматического преобразования float в пару Modbus-регистров.

## MQTT

Параметры `broker` (`mqtt://…` или `mqtts://…`), `clientId`, `username`,
`password`, `subscribeTopic` настраиваются до включения сервиса. Для изменения
параметров выключить и включить клиент. MQTTS проверяет сертификат по root bundle.
QoS 0/1, retain, keepalive 30 с, автоматическое переподключение.

Для публикации задать `publishTopic`, `publishPayload`, вызвать `publish`.
Входящие данные: `receivedTopic`, `receivedPayload`, счётчики `received/dropped`.
Один клиент; входящая очередь 8 сообщений, payload до 256 байт, topic до 127 байт.
Буферы не являются готовыми числовыми MQTT-точками: числовое форматирование и
прикладное связывание с IO выполняется отдельно. Старый kit communityMQTT
остаётся Linux-модулем; на ESP32 используется новый bclimateEsp32::MqttService.

## Диагностика

Обновляется раз в секунду. `cpu0/cpu1` — оценка занятого времени каждого ядра
по idle task за интервал, проценты; значения не складываются в один процент.
`freeHeap/minFreeHeap/largestFreeBlock/vmStackFree` — байты.
`periodAvgMs/periodMaxMs` — период между циклами, включая ожидание, а не время
чистого исполнения алгоритма. `overruns` — накопленное число нарушений срока.

## HTTPS OTA

`OtaService.url` — URL файла приложения `.bin` по HTTPS. При пустом `caCert`
используется root bundle, для частного сервера можно задать PEM CA.
Часы синхронизируются SNTP через `SEDONA_NTP_SERVER` (по умолчанию pool.ntp.org).
Если сеть не даёт NTP, записать Unix UTC в `utcSeconds` и вызвать `setClock`.
Установить `enabled=true`, затем вызвать `update`.

`phase`: 0 idle, 1 download, 2 готов к перезапуску, 3 ошибка;
`percent` — ход скачивания. После успешного обновления плата перезапускается.
Образ подтверждается после не менее 30 секунд работы VM с scan watchdog;
сброс до подтверждения приводит к откату.

Сохранены factory 0x10000 и storage 0x210000; добавлены otadata 0x400000,
ota_0 0x410000 и ota_1 0x610000 (по 2 МиБ). Полный USB flash заново пишет
storage и otadata. После OTA адрес текущего приложения нельзя считать равным
0x10000: для обновлений использовать OTA, а не произвольную запись app-only.

OTA обновляет **только код прошивки**. kits.scode/app.sab не перезаписываются:
они должны быть совместимы с набором native-методов новой прошивки.
Обновление китов/приложения выполняется отдельно штатным механизмом Sedona.

## Результаты проверки

- На P4: 10854 assert, 0 ошибок; тесты не включают физические выходы.
- На симуляторе: 10853 assert, 0 ошибок.
- GPIO: реестр владельцев, allowlist, валидация, порядок установки latch,
  чтение/запись/освобождение и ошибки драйвера — mock-тест PASS.
- RTU: production master и slave через программный UART — все 8 FC,
  CRC, timeout, исключения, очистка UART; отдельные проверки malformed frames.
- Миграция: 24 существующих компонента и 5 связей сохранены; 49 всего.
- На P4 MQTT: CONNECT, SUBSCRIBE, приём, публикация QoS1, echo брокера PASS.
- На P4 HTTPS OTA: переход factory→ota_0, загрузка и подтверждение образа PASS.
- На P4 rollback: ota_0→ota_1, принудительный сброс до подтверждения,
  возврат в ota_0 и здоровый запуск PASS.

Электрические испытания AI/AO/DI/DO/счётчика, RS-485 с трансивером, SPI/I²C
с подключёнными устройствами ещё не проводились. Наличие компонента и успешная
сборка не заменяют эти испытания.
